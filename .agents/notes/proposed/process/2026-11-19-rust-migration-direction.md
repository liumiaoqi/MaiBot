# Agent Note: MaiBot 缓慢 Rust 化方向

Status: proposed（2026-11-19 方向登记，非当务之急）

> **2026-11-20 候选顺序更新**：配置引擎已定为**第一个** Rust 件（不再是"等真实需求触发"），本文 §候选顺序 的顺位 1 从"若走 B 形态"变为确定项。判据与"不在早期迁移"清单仍有效。见 [`2026-11-20-config-rewrite-decision.md`](2026-11-20-config-rewrite-decision.md)。

## Problem

项目长期有意向 Rust 缓慢迁移，参照 Linux / Git 的做法：不重写核心，逐步用 Rust 替换一部分部件。但当前没有成文的原则，导致两个风险：

1. 每次讨论都从零开始，"要不要用 Rust"反复消耗；
2. 容易把 Rust 用在错误的边界上（热路径跨语言调用），把简单问题做复杂。

同时必须承认：**当前真正的阻塞不是语言**。Phase 3 的 config 形状未定、104 域未接、组合系统未定——这些问题与用 Python 还是 Rust 无关。

## Decision（proposed）

采用「边缘优先、旁路替代、不重写核心」的迁移原则：

**判据（同时满足才适合先迁）**

1. 边界清晰：能独立成一个二进制、CLI 或库；
2. 不与 Python 生态生命周期纠缠（pydantic schema、asyncio、FastAPI 依赖注入、端口契约）；
3. 可独立测试，不依赖运行中的主进程；
4. 有明确收益（性能 / 内存安全 / 跨语言复用），而不是"为了用 Rust"。

**候选顺序**

| 顺位 | 候选 | 理由 |
|---|---|---|
| 1 | 配置组合器 / 校验器（若走 B 形态：离线生成正本） | 纯函数、边界清晰、可独立测试 |
| 2 | 日志 / 遥测聚合 | 数据量大、逻辑独立 |
| 3 | 消息协议编解码 | 边界清晰，与 NapCat 协议对齐即可 |
| 4 | 记忆索引底层 | 需先测量，A_memorix 已用 FAISS，未必需要 |
| 5 | 插件 runner 宿主侧 | 已有 gRPC 隔离，收益低 |

**不在早期迁移**

- Orchestrator / 思考管道（pydantic + asyncio + 端口契约耦合最深）；
- WebUI 后端（FastAPI / pydantic）；
- 配置模型与热重载（生命周期耦合）。

**接入方式**

- 优先 CLI / 独立进程，通过文件或 gRPC 交互；
- 不在热路径上做 subprocess 往返，不用 PyO3 暴露 pydantic 模型；
- 迁移一个部件时，接口先冻结，再换实现。

## Alternatives considered

- **全量重写 Rust**：与 Linux/Git 的经验相反，且会同时引入第三个技术栈，构建/CI/容器/agent 协作成本激增——拒绝。
- **不迁移，永久 Python**：放弃长期性能与内存安全收益；但对当前功能没有硬伤，所以列为"可接受现状"。
- **先迁移核心（Orchestrator）**：生态耦合最深、验证面最大，风险最高——拒绝。
- **为方向先引入 Rust 工具链**：没有第一个合格试验田之前引入，只会增加空转成本——拒绝。

## Consequences

- **多栈成本**：Python + TS + Rust 三套构建链；CI、容器镜像、版本锁定都要同步维护。
- **协作成本**：多语言会提高 agent 理解与修改门槛，需要明确的边界文档。
- **迁移顺序绑业务**：第一个 Rust 部件应由真实需求触发（例如选 B 形态做配置组合器），而不是先定语言再找场景。
- **不回滚承诺**：本 note 只登记方向与判据，不构成本期实施承诺。

## 与当前任务的关系

- 当前仍从 `#2(b)` 前端接缝迁移开始——它是解阻点，与语言无关。
- 若将来配置组合系统选 B 形态，其离线组合器就是第一个天然试验田；届时再引入 Rust。
- 若选 A 形态（运行时解析），组合器应与 Python 主进程同栈，不应用 Rust 跨边界。

## 验收（未来首个迁移部件时）

- 接口冻结在前，实现替换在后；替换前后行为逐字节/逐字段一致；
- 不新增热路径跨语言调用；
- 构建与 CI 能独立跑该部件的最小验证集；
- 有明确收益证据（基准或缺陷类型），不是主观偏好。
