# CPU 小语言模型 — 项目笔记（想法记录）

> 最后更新：2026-08-05
> 状态：🏗️ 开发中（mini SSM 字符级 → BPE 升级中）

## 项目目标

开发一个真正适合 CPU 的架构的小语言模型（存储/算力成本低），
用公开小语料（游戏文案/歌词）训练，验证"能说话"的最小规模。

## 设计想法（lmq，2026-08-05）

### 1. 本地小模型 + API LLM 混合架构（重要设想）

```
API LLM（DeepSeek）──对话理解/转译──→ 受限词汇序列 ──→ 本地小模型（角色词库）──→ 风格化输出
```

**2026-08-05 落地形态更新**：8 个神经网络实验（SSM/SWA/Transformer × 字符/BPE/受限/混合/GPU）全部失败后，
"本地小模型"确定为**规则风格引擎**（style_engine.py，n-gram + 词库 + 模板，零训练）：
- 词库 300 词（vocab/role_希儿.txt，可手动编辑）+ 2-gram 3,268 / 3-gram 6,425 条件 → 583KB JSON
- 生成示例："布洛妮娅……哼。""对不起Veliona！你是你自己。""永远……哼。"
- 台词×3 加权是风格关键（引号内台词优先于设定叙述）
- 代价：只能复现统计过的组合，无泛化——"理解靠 API"部分保持不变
- 2026-08-06：**分层引擎 v1（hierarchical_engine.py）——"预装 + 学习"落地**
  - 认知（lmq）：人类学语言 = 进化预装 + 后天校准；随机初始化网络 = 从零 → 8 实验失败根源
  - 三层：状态机（手写意图→状态规则，预装"推理"）+ 句式模板/动作域（预装"语言结构"）
    + 填词（n-gram 条件分布查表，可替换为小网络学"填充"窄任务）
  - 生成示例："布洛妮娅姐姐，陪着。""希儿想要一直在一起。""嗯？有危险……"
  - 语义约束关键：状态动作域（依赖→陪着/做到；战斗→反击/守护；温柔→守护/相信）
  - 第三层升级路径：小网络只学"模板空位填词"（窄任务分类，非 next-token 生成）

- **分工**："理解靠 API，风格靠本地"——API 负责语义理解，本地负责"用这个角色的方式说"
- **依据**：角色所用词汇非常少（几百个词元）→ 本地模型 vocab 极小 → 参数可做到 100K 级（几百 KB）
- **类比**：上位机（API）做逻辑运算，PLC（本地）按配方词库执行
- **边界**：受限词汇的本地模型"思考" = 学过的词元组合模式重现（马尔可夫式），不是真推理；
  它负责"用角色的方式说"，不负责"想清楚说什么"
- **落地形态**：每个角色一个本地风格模型（几百 KB 存储），共享一个 API 理解层
- **状态**：设计方向，待 BPE 版本验证后评估

### 2. 手动词元（角色词汇表）

- `vocab/custom_tokens.txt`：每行一个词（角色名/专有名词），**优先匹配不被 BPE 拆散**
- 角色词汇少 → 手动词元表就是角色的"全部词汇"——本地模型的表达域
- 用户可手动划分（基于语料阅读/角色理解），也可以后续从语料统计候选

### 3. BPE 升级动机

- 字符级的问题（实证）："儿儿儿"卡死——模型学到"希"后必跟"儿"，
  没学到"希儿"是名字——字符级只能学字与字的组合，BPE 学词与词的搭配
- BPE 收益：序列短一半（信息密度高）、词级规律、生成步数少
- 中文 BPE 平均 1-2 字/token

### 4. 语料

- 当前：`data/corpus.txt`（98.6 万字符，来自"整理崩坏星穹铁道资料"378 个 md）
- 计划：加歌词语料（公开小语料）对比——歌词重复结构 vs 游戏文案角色语气
- 小参数模型学风格快（参数小 = 只能抓最显著的统计模式）

## 实验记录

- 2026-08-05：mini SSM 956K 参数（d=128, l=2）训练 3 epoch，loss 8.15→0.009
  - CPU 71 秒/epoch（Windows uv 环境）
  - 生成卡"儿儿儿"（字符级 + 过拟合高频字符）→ 升级 BPE
- 2026-08-05：BPE tokenizer 实现（自定义词元优先 + 词内合并，目标 vocab 4000）
- 2026-08-05：**A+B 方案执行（混合语料 + 强正则化）**
  - A：`corpus_mix_希儿.txt` = 希儿 169,271 + 资本论 236,824 = **406,096 字符**（用户提供资本论.txt）
  - B：mini_swa 正则化 dropout 0.4 / weight_decay 0.1 / label_smoothing 0.1
  - 训练 6 epochs：loss 6.35 → 1.54 → **停滞 1.21**（epoch 4 后几乎不动）
  - **生成仍全部复读**（24 组 prompt×温度测试，唯一字符比例 0.02~0.29）
  - **结论：A+B 未解决复读**。loss 1.2 对 vocab 4000 不算高——模型学了不少却输出尖锐重复，
    指向**采样/分布问题**（高频 token 概率过高、长尾没学会），不是单纯过拟合；
    温度 1.3 复读率明显改善（0.28 vs 0.04）佐证输出分布过尖
  - **GPU 对照（同语料同正则化，RTX 5060，torch cu130）**：Transformer 6 epochs loss=**1.2006**（CPU 版 1.2007，完全一致）
    → **复读与架构无关**：SWA 1.21 ≈ Transformer 1.20，同数据同正则化收敛到同一点
  - 环境：pyproject 显式声明 torch 直接依赖 + cu130 索引（sources 只对直接依赖生效的坑）
  - **最终结论：1M 参数 × 40 万字符 = 容量-数据-分布三角死局**
    1. 容量：1M 参数 ≈ 100 万条关联；4000 token 的转移矩阵 1600 万条目，只能记最高频 5%
    2. 数据：LLM 经验法则参数≈token×20-30 → 1M 参数需 2000-3000 万 token，现有差 150 倍
    3. 分布：softmax 把高频 token 概率推极尖（"希儿→希儿" >0.5），top_k 必然陷入高频环（温度 1.3 缓解佐证）
    → 出路：**受限词库 300-500 token 的角色模型**（转移矩阵 ~20 万条目，1M 参数够用）
      = NOTES.md 的本地+API 混合架构的数学依据（"理解靠 API，风格靠本地"）
  - GPU 利用率 ~5%：1M 模型计算量太小，GPU 空转等 CPU 喂数据——**小模型硬件匹配是 CPU**（knob 实验结论再实证）
- 2026-08-05：**受限词库/语料结构实验（R/D/CF，8 个实验全部失败的收敛）**
  - R：top-400 词库 + <unk>（vocab 401，334K）→ **<unk> 黑洞**（语料 39% 是 <unk>，模型学会输出 <unk> 保命）
  - D：全部角色传记台词+上下文（266K，3,096 条台词，web_import_tmp）→ <unk> 黑洞更重
  - CF：词 400 + 字符回退（vocab 2,984，998K）→ <unk> 消失但**单字复读回归**
  - 覆盖率曲线：任何 30 万字符语料 top-400 覆盖 ~60%（台词并不比设定文档集中）
  - **最终结论（跨 8 实验）**：
    ① 复读/黑洞与架构无关（SWA=Transformer=SSM）、硬件无关、正则化无关
    ② vocab 结构决定失败形态：词级→复读，纯受限→黑洞，字符回退→单字复读
    ③ **<1M 参数 × 30 万字符 × next-token 自由生成中文 = 不可能三角**
    ④ 出路：非 next-token 任务形态（条件选择/分类目标 + beam search）或
       n-gram+规则 风格引擎（用户 NOTES.md 1. 的"PLC 按配方执行"愿景）——**已实现 style_engine.py**
  - 环境：pyproject 声明 torch 直接依赖 + cu130（sources 只对直接依赖生效）；RTX 5060 可用
